# S13 인터뷰 절차

요구서 인터뷰의 표준 절차다. 원본 저장소의 하네스 가이드에 설계로만 있던 내용을 키트에서 쓸 수 있게 옮겼다. 양식은 `docs/requirements/_template.md`와 `docs/requirements/_template.contract.json` 한 곳뿐이고, 이 파일은 묻는 방법만 정한다.

## 방식

- 사용자가 만들고 싶은 것을 한 줄로 말하면, 이해한 내용을 먼저 되짚고, 원천을 조회한 근거를 보여 주며 묻는다.
- 질문은 "기본안 + 확인"이다. AI의 최선의 기본안을 먼저 내고, 사용자는 예/아니오로 답한다. 정의를 처음부터 만들게 하지 않는다.
- 사용자는 데이터 전문가가 아닐 수 있다. 전문 용어는 처음 나올 때 풀어 쓴다(예: "그레인 = 결과 테이블의 한 줄이 무엇을 뜻하는지").
- 답하는 사람은 요청자다. AI가 스스로 채운 칸은 "가정"으로 적고 마지막에 한 번에 확인받는다.

## 흐름

1. **문제 확인**: 목적, 쓰는 사람. 만들 수 있는 집계의 예를 컬럼 이름에서 3개 보여 주되 고르는 것은 사용자다(incremental이면 일 단위 지표인 예만). 추천하지 않는다.
2. **데이터 확인**: 아래 고정 조회 7종을 모두 돈다.
3. **정의 확정**: 지표, 집계 기준일, 집계 단위(그레인)의 기본안을 하나씩 묻는다.
4. **검증 기준**: 정의마다 contract check를 만들고 요구 ID(`R-01`…)와 잇는다.
5. **가정과 범위**: AI가 채운 칸(가정)과 이번에 하지 않을 것(범위 밖)을 한 질문으로 확인.
6. **결재 요약**: 작업 목록, 층 구조, 결과 한 줄의 모양을 쉬운 말로 보여 주고 확인. 사용자에게 보이는 말에서 raw → stg → mart는 "원본 복사 → 정리 → 결과 표"로 쓴다(파일·contract 안의 이름은 그대로).

## 마트 이름

AI가 기본안을 낸다: 결과 한 줄의 모양을 담은 영어 소문자·밑줄 이름, `mart_`로 시작(예: `mart_daily_trips`). 사용자에게 처음부터 짓게 하지 않고 "기본안대로 / 아니오 (바꿀 이름은 기타에)"로 확인만 받는다.

## 이 키트로 안 되는 요청

안 되는 이유를 아래 문장 그대로 한 번 말하고, 가장 가까운 가능한 형태를 기본안으로 내어 질문을 이어 간다.

| 요청 | 이유 문장 | 가장 가까운 기본안 |
|---|---|---|
| 여러 데이터셋을 섞기 | 승인, 개인정보 검토, 원본과 맞는지 검사가 모두 데이터 하나를 기준으로 짜여 있습니다. 같은 데이터 안의 표끼리는 합칠 수 있습니다. | 고른 데이터셋 안의 표만으로 만든 결과 표 |
| 실시간 | 이 키트는 하루 단위로 묶어 처리합니다. | 하루 단위 결과 표 |
| 예측 모델 | 예측이 맞는지는 코드가 자동으로 판정할 수 없습니다. 이 키트는 자동으로 검사할 수 있는 결과 표만 만듭니다. | 예측에 쓸 과거 집계 결과 표 |
| 큰데 날짜 구분이 없는 표 | 한 번에 읽는 양에 비용 상한(500 MB)이 있습니다. | 같은 데이터의 다른 표(S9) 또는 다른 데이터(S8) |

## 고정 조회 7종 (모든 마트 공통)

조건: `ai-builder` 계정(설정 그대로), 읽기 전용, 모든 `bq query`는 `--dry_run`을 먼저 돌리고 본 실행에는 `--maximum_bytes_billed=524288000`. 결과는 집계값만 인터뷰 기록에 남기고 행 단위 값은 남기지 않는다. 쿼리 원문은 인터뷰 기록의 "근거 쿼리" 절에 둔다.

| # | 조회 | 무엇을 보나 |
|---|---|---|
| 1 | 값 분포 | 상태·유형 컬럼의 값별 건수(상위 몇 개) |
| 2 | 빈 값 비율 | 쓸 컬럼마다 NULL 비율 |
| 3 | 기간 | 시각 컬럼의 최소·최대, 날짜별 건수의 시작·끝 |
| 4 | 키 후보 중복 | 키로 쓸 컬럼 조합의 중복 행 수 |
| 5 | 조인 시 행 증가 | 조인 전후 행 수 |
| 6 | 개인정보 후보 | 아래 "개인정보 후보 찾기" |
| 7 | 원천 크기와 날짜 파티션 | 아래 "크기와 적재 방식" |

조회로 찾은 위험(예: 조인 시 행 증가, 미래 시각, 빈 값)은 인터뷰 기록의 "위험 항목"에 적고 완료 조건 검사로 잇는다.

## 크기와 적재 방식 (조회 7)

메타데이터로만 본다. S9의 `check_source.py` 판정표(손으로 하는 길에서 날짜별 추가 적재를 볼 때는 `--allow-large`)가 있으면 그 값을 쓰고, 인터뷰 중 쓸 테이블이 바뀌면 다시 돌린다.

- 테이블 크기: 원천 데이터셋의 `__TABLES__`(`size_bytes`, `row_count`, `type`)
- 날짜 파티션 컬럼: `INFORMATION_SCHEMA.COLUMNS`의 `is_partitioning_column`

기본안 규칙:

- 쓸 테이블이 모두 500 MB 이하 → `snapshot`(기본값)
- 500 MB를 넘는 테이블이 있음 → 그 테이블에 날짜 파티션이 있을 때만 `incremental`. `load.date_column` = 그 파티션 컬럼, 일 단위 지표만
- 둘 다 아님 → 아래 "이 키트로 안 되는 요청"의 "큰데 날짜 구분이 없는 표" 문장을 말하고, 다른 테이블(S9) 또는 다른 데이터(S8)를 기본안으로 낸다
- 뷰(`type` 2)는 크기로 판단하지 않는다. 날짜 파티션이 없어 `incremental`을 고를 수 없다. 쓸 컬럼만 읽는 쿼리의 dry-run 바이트가 500 MB 이하일 때만 `snapshot`
- 고른 방식은 요구서 2절 "적재 방식"과 contract `load`에 적는다. `incremental`이면 "원천에 데이터가 있는 마지막 날짜"를 조회해 인터뷰 기록에 적는다(S15의 `--ds`에 씀)

## 개인정보 후보 찾기 (조회 6)

- 원천의 `INFORMATION_SCHEMA.COLUMNS`에서 컬럼 이름만 본다. 데이터 값은 조회하지 않는다.
- 컬럼 이름을 밑줄(`_`)로 나눈 단어 중 하나가 email, name, phone, address, ip, latitude, longitude, lat, lon, birth, postal, zip, geom 중 하나와 같으면 후보다. 예: `ip`, `ip_address`는 걸리고 `trip`은 걸리지 않는다.
- 후보(테이블, 컬럼, 걸린 단어)만 인터뷰 기록에 적는다. 확정은 S11에서 사람이 했고, `docs/architecture/pii_columns.md`의 컬럼은 stg·mart로 넘기지 않는다.

## 질문 (AskUserQuestion)

- 판단 질문(지표 정의, 기준일, 테이블 구성, 그레인)은 한 번에 하나, **모두 합쳐 최대 6개**. 6개 안에 못 정한 칸은 기본안을 "가정"으로 적고 흐름 5에서 한 번에 확인한다. 서로 독립적인 간단한 확인(갱신 주기, 보관 기간)은 한 창에 최대 3개까지 묶는다.
- 질문 수나 걸리는 시간은 미리 말하지 않는다. 진행 표시는 질문 창 header의 `질문 3/6` 같은 번호뿐이다(분모는 6).
- 질문 문장: 무엇을 정하는지 + 근거 한 줄(집계값). 예: "매출을 어느 날짜에 셀까요? 주문 시각과 배송 완료 시각이 있고, 배송 완료 시각은 주문의 37%에만 있습니다."
- 첫 선택지: **기본안대로 (권장)**, 설명에 기본안 내용. 나머지: 다른 안 1~3개. 계산 방법은 쉬운 말로 쓰고("차이법" 같은 이름 대신 무엇에서 무엇을 빼는지), 영어 칸 이름 옆에는 한글 뜻을 붙인다(예: `trip_count`(이용 건수)). 예/아니오 질문은 "아니오 (바꿀 내용은 기타에)" 하나.
- 미리보기: 그 안으로 나올 결과를 쉬운 말로(예: "날짜마다 한 줄, 칸은 날짜·주문 수·매출 합계"). 데이터 값은 넣지 않는다.
- "기타"에 쓴 답이 기본안과 다르면 다음 질문 전에 "이렇게 이해했습니다" 확인을 한 번 더 한다.
- 사용자 대신 "기본안대로"를 고르지 않는다.

## 금액 타입 (NUMERIC)

금액, 합계를 담는 stg·mart 컬럼은 고정소수점(NUMERIC)으로 제안한다. 부동소수점(FLOAT64)이면 합계 검사가 끝자리 차이로 통과하지 못한다. 인터뷰 끝에 contract의 stg·mart 컬럼 타입을 다시 읽어 FLOAT64가 있으면 그 컬럼을 이름으로 짚어 예/아니오로 묻고("이 컬럼을 NUMERIC으로 바꿀까요?"), 답을 인터뷰 기록에 남긴다. 저장 때 Hook도 FLOAT64를 알려 준다.

## 기록과 출력

- 파일 3개(`<마트>`는 사용자와 정한 영어 소문자·밑줄 이름, `mart_`로 시작):
  - `docs/requirements/<마트>.md`: `_template.md`의 1~10절. 1~7절과 9·10절은 반드시 채운다(9절이 비면 L0 실패)
  - `docs/requirements/<마트>.contract.json`: `_template.contract.json` 형식. 지표는 `interview.metrics[]`, 검사는 id·문장·`rung`·`written_by`만(검증 쿼리 SQL은 루프의 verifier가 쓴다)
  - `docs/requirements/<마트>_interview.md`: ① 문제 확인, ② 데이터 확인(고정 조회 결과 요약과 근거 쿼리 원문), 위험 항목, ③~⑤ 질문과 답(질문, 기본안, 근거, 답을 그대로), 가정, ⑥ 결재 요약
- **한글 이름과 설명을 반드시 채운다**: 모든 테이블의 `name_ko`, 모든 컬럼의 `name_ko`와 `description`. L0는 `name_ko`가 없어도 통과하지만 비면 정의서 칸이 "미작성"으로 남는다. 승인 1 커밋 전에 `python .claude/skills/data-harness/scripts/check_spec_fields.py docs/requirements/<마트>.contract.json`을 돌려 종료 0인지 확인한다(1이면 나온 칸을 채우고 다시).
- 검사 문장(`checks[].rule`)에는 작은따옴표, 중괄호, 역슬래시, 줄바꿈을 쓰지 않는다. `requirements[].section`은 따옴표 없는 숫자 1~9.
- contract를 저장할 때마다 Hook이 L0를 돌린다. 오류가 나오면 그 자리에서 고친다. 끝나면 `python scripts/ladder/l0_contract.py docs/requirements/<마트>.contract.json`으로 한 번 더 확인한다(종료 0).
- 사람이 승인(결재 1)하기 전에는 루프를 시작하지 않는다.

## contract 형식 규칙 (L0가 보는 것)

아래 요약으로 쓴다. `scripts/ladder/l0_contract.py` 원본은 읽지 않는다. 오류가 나오면 오류 줄대로 고친다.

- 공통: 양식에 있는 칸만 쓴다. 없어도 되는 칸은 `reverts_to`·`requested_by`·`load`·`name_ko`뿐이고, 나머지 글자 칸은 비우지 않는다. 이름(마트, 테이블, 컬럼, task)은 영어 소문자로 시작하고 소문자·숫자·밑줄만. `version`은 1 이상 정수, `requested_by`는 null이나 `requester1` 같은 역할 코드
- `requirements[]`: id는 `R-01` 형식(중복 없음), `section`은 숫자 1~9. 요구마다 `traces_to`에 이어진 검사가 1개 이상
- `sources[]`: `<설정의 원천 프로젝트>.<데이터셋>.<테이블>`, 중복 없음
- `interview`: `metrics[]`는 name(중복 없음)·formula·unit·base_date·exclude를 모두 채우고, numerator·denominator는 둘 다 쓰거나 둘 다 null. `keys`·`assumptions`·`out_of_scope`는 비지 않은 목록
- `dag.tasks[]`: kind는 `load`·`gate`, layer는 `raw`·`stg`·`mart`. 적재(load)가 있는 층마다 게이트 1개, 게이트 id는 `gate_<층>_<마트>`. upstream은 있는 task만(순환·자기 자신 안 됨), mart 적재는 raw를 직접 읽지 않음
- `tables[]`: 적재 task 1개에 테이블 1개, 층이 task와 같음. `keys`는 비지 않고 그 테이블 컬럼 안에. 컬럼 타입은 BigQuery 타입(STRING, INT64, NUMERIC, BIGNUMERIC, FLOAT64, BOOL, DATE, DATETIME, TIMESTAMP, TIME, BYTES, JSON, GEOGRAPHY, INTERVAL, ARRAY, STRUCT). 개인 식별 컬럼은 stg·mart에 두지 않음
- `load`: `{"mode": "snapshot"}`이면 다른 칸 없음. `incremental`이면 `date_column`·`partition_column` 필수(모든 테이블에 그 이름의 DATE 컬럼), `allow_empty_days`는 true·false
- `checks`: `gates`는 id `C-01` 형식·rung L3, `reconciliation`은 `C-`·L4, `invariants`는 `I-`·L4나 L5. 셋 다 1개 이상, id는 전체에서 중복 없음, `written_by`는 모두 `verifier`
- `traces_to[]`: 있는 요구와 있는 검사를 잇고, `rung`은 그 검사의 rung과 같음
- `schedule`: `refresh`는 글자, `retention_days`는 null이나 1 이상 정수. `modules.expert`의 `on`은 빈 목록, `version`은 null(양식 그대로)
